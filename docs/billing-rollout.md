# LeadFlow billing rollout

LeadFlow bills each workspace as one company. New workspaces start with 336 hours of Starter trial. Existing workspaces get a fresh 14-day rollout window; their initial tier fits the existing roster. Plans are 699, 1499, and 2999 EGP per month with 3, 10, and unlimited seats. Annual payments cost ten monthly installments and extend access by twelve calendar months. A downgrade over the current seat cap needs a smaller roster before approval. Renewal extends the later of the expiry date or database time; collecting a payment does not lift a suspension.

Use `PAYMENT_PROVIDER=manual` and configure `PAYMENT_INSTAPAY`, `PAYMENT_VODAFONE_CASH`, and `PAYMENT_BANK_DETAILS` in the server environment. Empty destinations are disabled. Configure `BILLING_OWNER_IDS` as comma-separated, immutable Supabase Auth user IDs for trusted platform operators. Company owners only see and submit payments for their workspace. Platform operators open **Billing > Manage companies**. The service-role key stays on the server. No payment gateway or webhook is active. Verify each transfer in the receiving account before confirming it; a screenshot is not settlement evidence.

Keys become required for a company once its first key is issued. Revoking the active key blocks existing activations until a replacement is issued and activated. The device ID represents an installation/browser profile, is reset by clearing site data, and is not hardware attestation. Production use requires HTTPS. Receipt images are stored in a private bucket and operator links expire after 60 seconds.

New keys use seven groups of four characters (`LEAD-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX`) from a 32-symbol alphabet, giving 140 bits of entropy. The full key is shown once, immediately after issuance. PostgreSQL stores its SHA-256 digest and four-character suffix; later admin responses include only the suffix. Legacy keys continue to activate with the same code after migration, but retain their original 32-bit strength. Rotate them, and handle pre-migration database backups as containing plaintext keys.

Five failed activation attempts within an inactivity window lock the company/device and company/account for 15 minutes. Changing the guess or resetting the browser installation does not reset the account counter. Activation failures use the same response. Device limits are Starter 3, Pro 10, and Business 20. Migration and later plan downgrades keep the earliest activations up to the applicable cap.

The admin audit view can filter by company. It shows the verified operator's Auth ID, date, action, and note. The admin RPC records the audit entry in the same transaction as the change. Reads go through the server's `BILLING_OWNER_IDS` check; ordinary authenticated users have no direct audit access. Historical actions are not reconstructed. A payment confirmed during suspension appears as **Paid - needs reactivation**; the operator must explicitly reactivate the company.

## Database

On a disposable local Supabase stack, run `supabase start` and `supabase db reset --local`. Run `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/billing-isolation.sql` against that local database. The test inserts fixtures in one transaction and rolls back. Do not run it against production. The canonical deployment chain is `supabase/migrations`; do not also replay the Drizzle baseline.

For an already populated Supabase instance, compare the remote migration ledger and a schema export with the checked-in chain on an isolated copy. If the core schema already exists but version `20261114000000` is missing, mark that version applied only after verifying the actual baseline objects and matching any drift. Do not replay it over live tables. Do not rewrite versions already applied. Confirm the billing starting state for existing customers before deploying. See the [official migration guide](https://supabase.com/docs/guides/deployment/database-migrations).

Run `bun run test` to exercise all nine migrations and the billing isolation suite on a local PostgreSQL engine (PGlite), with test substitutes for Supabase Auth and Storage. Coverage includes legacy key migration, lockout, audit, and suspended payment. For release, repeat against a disposable Supabase stack and exercise JWT and PostgREST permissions, email invites, sign-in, receipt upload, and the signed URL. Apply `20261120000000_billing_security_fix.sql` with a coordinated server deploy: the old server references the removed plaintext column and RPC signature. No hosted database has been migrated.

## Windows

The supplied archive did not contain an existing Tauri project. The added Tauri v2 wrapper uses `bun run desktop:dev` for the local Vite server and `bun run desktop:build` for the Windows installer. Set `LEADFLOW_DESKTOP_URL` to the deployed HTTPS origin before building. The desktop client loads the deployed app so TanStack Start server functions remain available, and grants no native capabilities to the website. An internet connection is required. See [Tauri Windows prerequisites](https://v2.tauri.app/start/prerequisites/). Build and smoke-test the installer on Windows with those prerequisites; this workspace did not have Rust/Cargo.
